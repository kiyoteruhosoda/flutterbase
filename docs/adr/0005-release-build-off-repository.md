# 0005. リリースビルドはリポジトリの外で焼き、その契約をこちらで検査する

- 状態: 採用
- 日付: 2026-08-24
- 置き換え: [ADR 0003](0003-build-in-dev-container.md)

## 文脈

配布する APK / AAB を焼く経路は、この 1 年で 3 回変わりました。

| 時期 | 経路 | 顛末 |
|---|---|---|
| 〜2026-08 | `.github/workflows/build.yml`（クラウドで self-hosted runner を起動） | 削除済み |
| 2026-08-03 | `scripts/build-remote-container.sh`（配布先ホストの dev コンテナ） | 定常運用に乗らないまま廃止（ADR 0003） |
| 2026-08-23〜 | ビルドホスト側のリリース経路（3 段構成） | **現行** |
| （常に） | `azure-pipelines.yml` | 一度も使われないまま残っていた |

リポジトリにはこの全部の痕跡が同時に残っていました。`azure-pipelines.yml` は
存在しない `ios/` をビルドし、終了したサービスへ配布し、`build.gradle` が読まない
環境変数で署名しようとする、という状態で 300 行あり、しかも `docs/` は
そこを「Flutter のバージョンを固定する 3 か所」の 1 つとして数えていました。

現行の経路は、署名鍵をアプリのビルドコードから隔離するために 3 段に分かれています。

| 段 | やること | リポジトリを見るか | 鍵を持つか |
|---|---|---|---|
| 1 | ビルド | 見る（アプリのコードが走る） | **持たない** → 未署名 |
| 2 | 署名 | 見ない | 持つ |
| 3 | 検証・保管 | 見ない | 持たない |

この分割には代償があります。**段 2 と段 3 はリポジトリを見ないので、成果物を
固定のディレクトリから固定の名前で拾うしかありません。**その名前を作っているのは
`android/app/build.gradle` の中の、他のどこからも参照されていないコピー処理と
`unsignedRelease` フラグだけです。

結果として、次の状態が成立していました。

- `build.gradle` のリネーム処理を消しても、**CI は緑**
- `NOLUMIA_SIGNING=none` の分岐を壊しても、**CI は緑**
- どちらもマージ後、ビルドホストで初めて落ちる

品質ゲートが焼いていたのは `flutter build apk --debug` だけで、release ビルド
タイプにも、リネーム処理にも、未署名モードにも一度も触れていなかったためです。

## 決定

### 1. リリースビルドはリポジトリの外にある、と認める

このリポジトリに CI からリリース成果物を焼く経路は置きません。`quality.yml` は
検査だけを行い、タグも打たず、配布物も作りません。リリース成果物の作り方は
`docs/RELEASE.md` に文章として置き、実体はビルドホスト側にあります。

**Flutter のバージョンを固定する場所は 3 つあり、そのうち 1 つはリポジトリの
外です。**ビルダーイメージに同梱された Flutter が実際の固定値なので、
`environment:` の床を上げるときは先にイメージ側を用意します。順序を逆にすると
CI は緑のままリリースビルドだけが落ちます。これは `docs/OPERATIONS.md` に
明記します。

### 2. リポジトリ側が守るべき契約を、機械的に検査する

`scripts/check_release_contract.sh` を置きます。段 1 をリリース経路と同じ順序で
走らせ、そのあとで段 2 と段 3 が探すものを 1 つずつ確かめます。

- 成果物が per-app 名で、AGP の出力先と Flutter CLI のコピー先の**両方**にあること
- ファイル名の版数が `pubspec.yaml` の `version` と一致すること
- `NOLUMIA_SIGNING=none` が実際に `signingConfig` を外していること
- Flutter CLI が決め打ちで探す既定名の APK も置かれていること
- 成果物に署名ブロックが無いこと
- APK の applicationId が `build.gradle` の宣言と一致すること

これを `scripts/ci.sh` の最後の検査とし、**`flutter build apk --debug` を
置き換えます。**

### 3. 派生アプリの登録に必要なものを、リネーム時に出す

`scripts/rename_app.sh` は、リネーム後に `docs/komodo-registration.md` を
生成します。ビルドホストに登録するための宣言（アプリ名・applicationId・鍵の
別名・証明書指紋の記入欄）と、鍵を発行してから指紋を埋めるまでの手順が
入っています。

## 理由

### なぜ「CI で release を焼く」ではなく「契約を検査する」なのか

CI に鍵を置かない、というのがそもそもの前提です。鍵を渡さずに焼ける以上、
CI が作れるのは未署名の成果物までで、それは配れません。だとすれば CI の仕事は
「配れるものを作ること」ではなく、**「配る側が読むものが揃っていることを
確かめること」**になります。

検査対象を「段 2 と段 3 が実際に探すパス」に限っているのはそのためです。
リリース経路の実装が変わればこの検査も変わりますが、そのときは
`docs/RELEASE.md` の表と一緒に動きます。

### なぜ debug ビルドを置き換えたのか、残さなかったのか

release ビルドは debug ビルドが通る範囲を含みます。Gradle / AGP / KGP の設定が
壊れていれば release でも落ちますし、release でしか通らない経路（R8、
リネーム処理、未署名出力）がそこに乗ります。両方焼くと CI の時間が倍になり、
得られるものは「debug 固有の失敗」だけです。それは `key.properties` を持つ
開発機で日常的に踏むので、CI で買う価値がありません。

### なぜ検査を build.gradle の中に書かないのか

`build.gradle` にアサーションを足せば、契約と検査が同じ場所に並びます。
ただしそれでは**リネーム処理を丸ごと消したときに検査も一緒に消えます。**
壊れ方として一番起こりやすいのがそれなので、検査は外に置きます。

### なぜ外部ツールを必須にしないのか

`unzip` と `aapt2` が無い環境では、その 2 つの検査だけスキップします。
中心的な検査（ファイル名と未署名出力）は `[ -f ]` だけで成立するように
設計してあり、素のツールチェインでも意味のある結果が出ます。

未署名かどうかを AGP の `app-release-unsigned.apk` というファイル名で判定して
いるのは、そのためです。AGP は `signingConfig` を持たないビルドタイプの出力に
だけこの名前を付けるので、外部ツールなしで `NOLUMIA_SIGNING=none` の効きを
直接読めます。

## 影響

- `azure-pipelines.yml` / `scripts/build-remote-container.sh` /
  `scripts/build-remote-container.env.example` を削除しました。
- `scripts/ci.sh` の最後の検査が `flutter build apk --debug` から
  `scripts/check_release_contract.sh` へ変わり、**CI の所要時間は伸びます。**
  release ビルドは APK と AAB の 2 本を焼くためです。`--fast` で従来どおり
  飛ばせます。
- `docs/` の「Flutter のバージョンを固定する 3 か所」から
  `azure-pipelines.yml` が消え、代わりにビルダーイメージが入りました。
  **3 か所のうち 1 つはこのリポジトリの外です。**
- `scripts/build.sh` は残ります（ADR 0003 の唯一の生き残り）。手元で任意の
  ブランチを焼く経路として有効です。
