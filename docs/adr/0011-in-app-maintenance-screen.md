# 0011. 対の Web の 503（メンテナンス・停止）で、アプリ内のメンテナンス画面に切り替える

- 状態: 採用
- 日付: 2026-10-23
- 課題: task #665（目的は #653「計画メンテナンス」）

## 文脈

予定して止めるとき、edge（公開名の前段の nginx）はメンテナンスの宣言があるホストへの要求すべてに
**503** を返す。ブラウザ（`Accept: text/html`）には edge のメンテナンスのページ、それ以外には JSON:

```json
{"error": "service_unavailable", "reason": "maintenance",
 "until": "2026-10-28T19:30:00Z", "message": "<理由>",
 "title": "<見出し>", "body": "<本文>"}
```

（`Retry-After: 300`・`Cache-Control: no-store`。`title`・`body` は #663 で足したもので、古い edge には無い。）
上流（対の Web）が居ないだけのときは `{"error": "service_unavailable", "reason": "stopped", "host": "…"}`。

このアプリは対の Web の API を `WebApiClient` で呼ぶ（ADR-0009）。これまでは 503 も他の失敗と同じ
`InfrastructureError` で、呼んだ画面ごとに黙るかエラーを出すだけだった。利用者には「壊れた」としか見えず、
いつ戻るかも分からない。目的 #653 で、雛形（fastapitemplate・flutterbase）にアプリ内の
メンテナンス画面を入れてから各アプリへ広げると決めた（2026-10-23 持ち主の決定）。

## 決定

**`WebApiClient` が edge の 503 を見分けて知らせ、アプリ全体の上にメンテナンス画面をかぶせる。
90 秒ごとに確かめ直し、戻ったら外す。**

- **見分け方**（`serviceOutageFrom`）: 状態が `503` で、本文が JSON の
  `{"error": "service_unavailable", "reason": "maintenance" | "stopped"}` のときだけ。
  503 でも HTML・空・別の形の JSON・知らない `reason` は、これまでどおりの `InfrastructureError`
  （Web 自身や別の中継の 503 を、メンテナンスと取り違えないため）。
  `title`・`body`・`message` は空なら無いものとし、`until` は ISO 8601 として読めなければ無いものとする
- **知らせ方**: 見分けた呼び出しは `ServiceUnavailableError`（`AppError` の新しい種類）で失敗し、
  同じものを `ServiceStatus.outages`（Application のポート。実装は `WebApiClient`）に流す。
  呼んだ画面の扱いは変わらない（どの画面も `on Exception` で受けている）
- **画面**: `ServiceOutageGate` を `MaterialApp.router` の `builder` に置き、
  止まっている間は `MaintenanceView` を全体にかぶせる。下の画面（router の Navigator）は
  **消さずに隠す**（`Offstage`・`TickerMode`）ので、戻ると元の画面・入力途中の文字のまま
  - 見出し・本文は edge の `title`・`body`。無ければアプリの文（メンテナンス中／停止中）
  - 理由（`message`）と戻りの見込み（`until`。**端末の時間帯**で、アプリの言語の日付と時刻）は、あれば出す
  - 「今すぐ確かめる」で待たずに確かめられる
- **確かめ直し**: 画面が出ている間だけ **90 秒ごと**（課題の「1〜2 分ごと」）に
  `GET /api/app/me` を**トークン無しで**送る。edge の 503 JSON ならまだ止まっている（中身は新しい方に
  入れ替える）。**それ以外の応答はすべて「戻った」**（401 も。edge が通したということ）。
  通信そのものが失敗したとき（圏外など）は何も分からないので、画面はそのまま次を待つ
- タイマーは `ServiceOutageGate` の State が持つ。画面が出ている間だけ動き、ウィジェットと一緒に消える
- サインインの無いビルドでは対の Web を呼ばないので、何もしない（購読もしない）

## 理由

- **見分けを `WebApiClient` の 1 か所にする。** 画面ごとに 503 を受けると、派生アプリが API を
  足すたびに書き漏れる。呼び出しの通り道で見分ければ、どの画面から呼んでも同じ画面になる
- **かぶせて、消さない。** メンテナンスをルートにして移ると、戻すときに元の場所を覚えておく必要があり、
  入力途中のものも消える。`builder` でかぶせれば router は何も知らずに済み、ディープリンクも壊さない
- **確かめ直しはトークン無しで。** edge は認証より前で答えるので、トークンは要らない。トークンを付けると、
  止まっている間にトークンが切れたとき「サインインが要る」と「止まっている」が混ざる
- **確かめる先は `/api/app/me`。** edge が閉じている間はどの道でも同じ 503 を返すので、どこでもよい。
  開いた後のために、雛形の対の Web にある口（fastapitemplate ADR-0045 の例の `GET /api/app/me`）を選んだ。
  トークンが無いので 401 になるが、それで「戻った」と分かる。派生の Web がこの口を消していても 404 で同じ
- **90 秒。** 課題の「1〜2 分ごと」の間。`Retry-After: 300` には従わない（5 分待たせると、
  戻ったのに画面が残る時間が長い。1 台が 90 秒に 1 度叩く程度は edge の負担にならない）

採らなかった案:

- **各リポジトリ・ユースケースで 503 を受けて状態を立てる** ——上のとおり書き漏れる
- **メンテナンス画面をルートにする** ——上のとおり、戻り先と入力が失われる
- **確かめ直しをやめ、利用者の「再試行」だけにする** ——課題が自動で戻ることを求めている
- **前もっての予告（帯）** ——目的 #653 で見送り

## 影響

- 依存は増えない
- 派生アプリは、`WebApiClient` を通して対の Web を呼んでいれば**そのまま**メンテナンス画面になる。
  派生アプリへ入れるのは別の課題（1 本ずつ）
- 対の Web が 503 を返す前（edge が古い・宣言が無い）は何も変わらない
- 対の Web 以外（assay のトークンの更新など）の 503 は見ていない
